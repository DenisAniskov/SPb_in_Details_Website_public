# Публикация исходного кода сайта — правила синхронизации (P7.12)

Этот репозиторий — **публичный, отдельно курируемый снимок исходного кода** официального сайта «Петербург в деталях». Его история Git независима от истории разработки. Публикация исходников **не означает** развёртывание сайта: production управляется отдельно.

## Принцип

- Переносить изменения **только через отдельную ветку и проверяемый Pull Request** в этом репозитории.
- Сверять содержимое нужных файлов с одобренной ревизией разработки; копировать только явно отобранные файлы. Не копировать ветки, коммиты, полную историю или все файлы исходного репозитория.
- Учитывать, что публичные README, инструкции, пути инструментов и настройки исключений могут **намеренно отличаться** от внутренних. Их нельзя без проверки перезаписывать.
- Не публиковать внутренние отчёты, планы, приватные конфигурации, токены, ключи, локальные пути, данные окружения, артефакты сборки или закрытые материалы.
- Для каждого **нового** пути отдельно утверждать назначение, происхождение, права на публикацию и необходимость в публичной версии. Автоматического разрешения для нового файла нет.

## Что проверять при каждом переносе

1. **База и объём.** Записать идентификатор одобренной ревизии разработки в описании PR (не переносить её историю). Проверить, что публичная ветка создана от актуального `main`; перечислить все добавленные, изменённые и удалённые пути.
2. **Код и ресурсы.** Переносить только нужные общие исходники (`src/`, `public/`, `scripts/`, `tools/`, конфигурацию). Перед добавлением скриншотов и графики проверить происхождение и права; правила `ASSET_RIGHTS.md` сохраняются.
3. **Публичные адаптации.** Отдельно просмотреть `README.md`, `.gitignore`, `scripts/verify-release-metadata.mjs`, `tools/generate_web_assets.py` и любые публичные инструкции. Не возвращать в них локальные пути или скрытые зависимости разработки.
4. **Версия.** Сверить `src/data/release.json` с фактически опубликованным Android-релизом: тег, версия, build, ссылка на APK, размер, SHA-256, сведения о подписи. Нельзя менять версию сайта только потому, что появился новый тег.
5. **Лицензии.** `LICENSE`, `ASSET_RIGHTS.md`, `README.md`, `src/pages/legal.astro` должны описывать одинаковые права. Полный текст MIT и `Copyright (c) 2026 Denis Aniskov` сохраняются. Проверить `package.json` и **корневую запись** `packages[""].license` в `package-lock.json`: обе должны быть `MIT`. `"private": true` означает запрет публикации пакета в npm, а не закрытую лицензию кода.
6. **Безопасность.** Просмотреть **весь итоговый diff и новое дерево** на секреты, приватные документы, абсолютные/локальные пути, URL закрытых служб и случайно включённые файлы. Игнорирование через `.gitignore` само по себе не защищает уже отслеживаемые Git файлы.
7. **Проверки.** В чистом checkout публичной ветки выполнить `npm ci`, `npm run check`, `npm run verify:metadata -- --github` и `npm run build`. Если проверки релиза требуют локального APK, использовать только разрешённый артефакт и не коммитить его. Обязательно сохранить результаты в PR.
8. **Приёмка.** Подтвердить, что PR содержит только разрешённые изменения и нет расхождений лицензий или метаданных. После merge проверить новый публичный `main`, доступность файлов и отсутствие автоматического развёртывания production.

## Запрещённые способы

- `git push --mirror`, перенос приватных веток и тегов, слияние несвязанных историй, `git filter-repo` над действующим публичным репозиторием без отдельного плана миграции.
- Массовое копирование каталога разработки прямо в публичный checkout; разрешается только **явно отобранный** набор файлов с последующим аудитом.
- Автоматическая публикация при каждом коммите разработки, без ручной проверки состава.
- Изменение production-конфигурации ради публикации исходников.

## После синхронизации

Зафиксировать в PR: ревизию источника, список файлов, причины публичных отличий, результаты сборки, контроль лицензий и итог ревью. GitHub Actions (`.github/workflows/public-website-ci.yml`, P7.13) выполняет read-only проверки кода, сборки и публичных метаданных на PR и после push в `main`; эти автоматические проверки дополняют, но **не заменяют** ручной аудит состава и прав на файлы. Workflow не разворачивает production.
